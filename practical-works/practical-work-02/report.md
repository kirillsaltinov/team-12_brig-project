### Распределение обязанностей по работе с репозиторием

*   **Славнов Н.А.** *(лидер команды, руководитель разработки ПО)*
    *   Следит за изменениями в проекте (коммитами) и помогает в упорядочивании файлов в репозитории.
    *   Проверяет все входящие Pull Requests, оценивает качество написанного кода и принимает решения о слиянии изменений в главную ветку.
    *   Пишет отчеты для практических работ (`report.md` в папках `practical-works-...`).

*   **Салтинов К.Е.** *(специалист по БД, тестировщик)*
    *   Выступает исполнителем на этапе создания и первичной настройки репозитория (настраивает файлы `.gitignore`, окружение для тестов).
    *   Совместно с лидером команды принимает участие в проверке Pull Requests.
    *   Фиксирует изменения при создании базы данных понятными коммитами, активно участвует в актуализации репозитория.

*   **Строгонов Р.Ю.** *(программист)*
    *   Ведет разработку сервиса через отдельные ветви, регулярно создает коммиты с подробными комментариями и отправляет их на проверку через Pull Requests.
    *   Строго следует структуре папок проекта, не допускает появления или своевременно избавляется от ненужных папок в репозитории, актуализирует код проекта.

*   **Телешинина З.С.** *(дизайнер)*
    *   Загружает в папку с ассетами дизайн-проект, графику интерфейса и иконки, строго соблюдая структуру папок проекта.
    *   Самостоятельно фиксирует все свои изменения через коммиты.
    *   Не принимает участия в обсуждении программного кода и слиянии технических веток проекта.

### Вывод
Система контроля версий позволяет всей команде, благодаря системе веток и пул-реквестов, одновременно работать над своими задачами, не перезаписывая код друг друга. Вклад каждого участника всегда заметен, так как Git закрепляет автора за каждым коммитом, что отображает реальный объем работы, проделанный участником. История изменений позволяет лидеру команды проверять код перед слиянием в главную ветку, а в случае неожиданных ошибок — дает способность выполнить откат к стабильной версии проекта.
